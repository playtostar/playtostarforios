=== 一、百科技能图门控（本轮最大风险面，此前零门控）===
百科是【主导航一级入口】（Layout.tsx:645 → /encyclopedia），
普通技能 44 张 + ST 技能 23 张 = 67 张图，来源为公司 COS 桶：
  .../EF20270916/EF2027/skill_icons/{PascalId}.webp
实测这些**不是图标，是游戏内实拍截图**：
  · 每张 288x173，画面是游戏 UI、球场、球员、技能释放特效；
  · Marking.webp 里球衣正面清晰印着 eFOOTBALL；
  · 文件名为游戏官方内部 Pascal 标识符。
此前这批图**完全没有 safeMode 门控**，审核员点进百科即可看到。
备注：旧版这里还挂着「图片素材来自网络」角标——这行字等于书面承认
「无授权仍在用」，是加罪不是减罪，本版已删除。

处置：
  1. EncyclopediaPage.tsx（列表页）
     const { safeMode, resolved: safeResolved } = useSafeModeState();
     const hideSkillImage = !safeResolved || safeMode;
     门控开启时渲染同尺寸 (aspect-[288/173]) 的 bg-white/5 灰块占位，
     布局不跳动。
  2. EncyclopediaDetailPage.tsx（详情页）同样双门控，整块 <img> 不渲染。
  3. 用 useSafeModeState() 而**不是** useSafeMode()，原因见下方
     「首帧竞态」——旧 hook 冷启动第一帧会按 false 渲染真图。

=== 二、安全模式首帧竞态修复（P0，会直接毁掉整轮整改）===
useSafeMode() 内部是 useState(cached ?? false)：冷启动时缓存为 null，
第一帧就按 safeMode=false 渲染。对于「只挡一张肖像图」的旧场景无所谓；
但本轮要整块藏掉热讯/V观点/百科图，这一帧就是**真实泄漏**，
审核员截屏完全可能抓到。
新增 useSafeModeState() → { safeMode, resolved }：
  resolved=false 表示「还没确定」，此期间所有门控一律按隐藏处理。
写成 hideXxx = !safeResolved || safeMode 即天然 fail-safe。

【UGC 板块门控（v10 起，本版继续有效）】
拒审判定的是「App 内容含未经授权内容」，UGC 是最大的不可控面：
文字层的第三方词可以过滤，但图片层不可控（官方卡面、真人肖像、第三方 logo），
视频 iframe 层完全不可控（B 站播放器加载后自带第三方封面/UP主名/标题）。

线上数据实测（全量拉取）：
  热讯 201 条，第三方词命中 12 条（6.0%），最早出现在第 17 位；
  V观点 60 条，第三方词命中 24 条（40.0%），最早第 25 位；
  作者名污染比标题更严重：V观点「实况起点」10 条 +「实况足球千月」5 条；
  热讯标签库 234 个去重标签里含 eFootball / 实况足球；
  抽样 36 张"文字干净"的配图，官方卡面/游戏内 UI 约 8-10 张、真人照片约 10-12 张、
  1 张直接印着 FOOTBALL 官方 logo。

处置（用户拍板）：
  热讯      → 整块隐藏
  V观点     → 整块隐藏
  论坛      → 保留，但审核期只渲染 3 条自写示例帖（描述本 App 自身功能，
              不含任何第三方商标/游戏名/授权形象）

⚠ 关键设计：隐藏 ≠ 安全。只从导航藏掉入口等于没做，因为：
  · 主导航「热讯」直达的是 /forum（默认 activeBoard='news'），不是 /news；
  · /news/:id 详情页内嵌 B 站 iframe，老分享链接/外部深链可直接命中；
  · RelatedVideos（球员/卡包详情页的"相关视频/相关热讯"）是独立入口；
  · /news/author/实况起点、/news/tag/实况足球 的 URL 里直接带第三方名称；
  · 个人中心 / 他人主页的「热讯」Tab 会列出标题+封面；
  · 论坛 "关注" 板混排帖子+热讯+V观点。
  故按 8 个入口全部封堵，且每个入口都走 useSafeModeState() 的 resolved
  双门控——开关未解析完时渲染骨架/空态，绝不先画一帧真内容。

【远程开关 fail-open 修复（v10 起，本版继续有效）】
原实现 fetchRemoteSafeMode() 是 fail-open——任何异常（网络错、非 2xx、JSON 解析
失败）都 return false，并且这个 false 会写进 localStorage 缓存 10 分钟。
已改为三态返回：
  true  服务器明确说开
  false 服务器明确说关
  null  没问到（网络错/超时/非 2xx/字段缺失/解析失败）
处理规则：
  · 只有明确的 true/false 才写缓存（"不确定"绝不固化成 10 分钟的"明确关"）
  · 没问到时：有历史已知值就沿用（哪怕过期），完全没有任何已知值才按安全侧
    true 兜底
  · 加 8s AbortController 超时，避免请求卡住导致页面无限等
  · 单飞 inflight Promise，避免并发重复请求

=== 四、App 内「自我声明审核关系」文案清零（本轮补漏，比官网更致命）===
官网已删「App Store 审核」字样后，回头扫 App 自身 bundle，发现还有 3 处
把「我正在被 Apple 审核」直接写在审核员能看到的界面上：

  1. Layout.tsx:90 / :96（网页端顶栏 Apple 图标 + 胶囊按钮）
       title="iOS 版正在 App Store 审核中"
       → title="iOS 版即将上线"
  2. i18n locales.ts:13 / :533
       'common.iosReview': 'iOS 审核中' / 'iOS In Review'
       → 'iOS 即将上线' / 'iOS Coming Soon'
  3. BetaAnnouncementDialog.tsx:99-108（公测公告弹窗）
       「iOS 版 App 正在苹果审核中，在此之前可直接使用网页版登录；
         受审核规则限制，网页端暂时仅支持…」
       → 「在此之前也可直接使用网页版登录；为保障账号安全，网页端目前采用…」
       EN 同步：删「The iOS app is under App Store review」「Due to review rules」

为什么这条特别危险：
  · BetaAnnouncementDialog 是**首次启动必弹**（localStorage 无
    pts_announce_v1 就 setAnnounceOpen(true)），审核员新装 App 一定看到；
  · 「我正在被 Apple 审核」等于把「这个 App 就是 4.1(a) 投诉对象」
    写在屏幕上；而 4.1(a) 判的正是「是否让审核员认为本 App 与被投诉方有关」；
  · 这是**自我指认**，比任何第三方商标都更直接。
注：Layout.tsx 那两处仅网页端渲染（isNativeApp() 时 return null），
    但 App bundle 与网页 bundle 是同一份源码产物，字符串照样进包，
    Apple 静态扫字符串一样能扫到，故必须一并清。
