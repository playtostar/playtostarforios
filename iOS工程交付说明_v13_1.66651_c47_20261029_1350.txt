=== 零、本轮五个新发现的风险点（上一轮 build 完成后才暴露）===

0.1 收藏页球员卡面泄漏（用户主动发现，本轮最隐蔽）
  ProfilePage.tsx 的「收藏-球员」子 tab 直接用 <img src={item.imageUrl}>
  渲染完整卡面 —— 它既不走 PlayerCard 也不走 TierPlayerCard，
  因此完全绕过了此前所有的肖像门控。路径：
    某球员详情页 → 点收藏 → 个人中心 → 收藏 → 球员 子 tab
  审核员走这条路径会看到一屏完整卡面，且此前无任何遮挡。
  处置：FavoritesSection 内改用 useSafeModeState()，
        hideFavPortrait = !favSafeResolved || favSafeMode 时
        渲染首字占位（item.title 首字），绝不回落到 <img>。
  为何用 useSafeModeState 而非 useSafeMode：见 v11 的「首帧竞态」，
  这里同样是整格内容级隐藏，不能用会先按 false 渲染的旧 hook。

0.2 三张分享图会画完整卡面（canvas 泄漏，比屏幕泄漏更彻底）
  分享图是 canvas 现画的，页面上的 <img> 门控对它完全无效：
    · player-share-image.ts  renderPlayerShareCanvas → 球员培养方案分享图
    · lineup-image.ts        renderLineupCanvas       → 阵容导出图
    · tier-image.ts          renderTierListCanvas     → 强度榜导出图
  三者在 safeMode 下仍会加载 COS 卡面并 drawImage 画进画布。
  后果：审核员点「保存图片 / 导出图片」，得到一张满是完整卡面的 PNG，
        而且这张图会存进相册、可通过相册分享外流 —— 泄漏程度远超屏幕。
  处置：三个生成器各加 safeMode 入参（默认 false，不影响网页端），
        为 true 时跳过卡面加载（imgMap 置 null / cardImg 置 null），
        走各生成器内既有的首字 fallback 分支 —— 不新增绘制逻辑。
        调用侧（PlayerDetailPage / MyLineup×2 / MyTierList×2）全部传入。

0.3 sitemap.xml 把网站路径明文带进 App 包
  app/client/public/sitemap.xml 是给网站做 SEO 的，被 dist→www 同步
  原样带进 Capacitor 的 webDir，再经 cap sync 复制到
  App.app/public/sitemap.xml 打进 .ipa。该文件含 9 条：

  这是包内唯一成规模的中文/游戏路径明文（vite.config.ts 的商标自检

  处置：打包脚本新增 SEO_ONLY_NAMES = {sitemap.xml, robots.txt}，

0.4 sourcemap 误报澄清（协同 AI 报告过，经核实不成立）
  协同 AI 称「index.js.map 15MB 被打进 App 包」。实测：
    · 交付 zip 0 个 .map；mobile/www 0 个；外部仓库 0 个
    · app/dist/client 0 个（打包脚本 clean_dist 按闭包外移了）
    · vite.config.ts 无 sourcemap 配置；MIAODA_BUILD_TARGET 全仓库 0 命中
    · codemagic.yaml 走 A 路径（www/index.html 存在）→ exit 0，不跑 vite build
  它扫的是 app/dist/web-efootball/assets/index-BTG3ZUgS.js.map（14.98MB，
  体积对得上），那是网站的构建目录，与 webDir 指向的 dist/client 无关。
  结论：不采纳其「加 MIAODA_BUILD_TARGET=standalone」的方案
        （那是 iife 单 chunk 形态，与 Capacitor 现用产物不一致，会改产物结构）；
        但其建议的 find -name "*.map" -delete 属纯防御，已一并加入 B 路径。

0.5 ★ 打包时误用「网页形态」产物（本说明 v12 定稿后才查出，已重出包）
  这是本轮最后一个、也是最容易漏掉的问题，记下来避免复发。

  现象：对 c47 包做全量商标词扫描，发现
        www/index.html            23 处命中
        www/assets/index-*.js      9 处命中（v11 时仅 2 处）
  两者都会 cap sync 进 .app，等于把中文品牌词明文送进 .ipa。

  根因：打包iOS工程.py 只负责「搬 dist/client → mobile/www」，**不构建前端**。
        我这一轮手工重建前端时只设了 NODE_ENV=production，**漏了 VITE_BASE=./**。
        vite.config.ts 里 IS_APP_BUILD =
            process.env.IS_APP_BUILD === '1' || BASE === './'
        漏了 VITE_BASE 就落回默认 BASE='/efootball/' → IS_APP_BUILD=false
        → 走「网页形态」分支，于是：
          <title>实况起点 PlayToStar｜球员数据·加点方案·强度榜</title>
          <meta name="keywords" content="实况起点,PlayToStar,足球游戏,...">
          <meta property="og:site_name" content="实况起点 PlayToStar">
          <link rel="canonical" href="https://playtostar.com/efootball/">
          <noscript>...实况起点 PlayToStar · 足球游戏球员数据社区...</noscript>
          bundle 内 /efootball/ 基础路径 ×7
        这些在网页上全是对的、必须的（SEO 就靠它们），但进了 App 包就是纯风险：
        App 内是 file:// 本地资源，SEO 语义零作用，只剩「中文品牌 + 站点子路径明文」。

  修复：用 APP 形态重建前端——
          export NODE_ENV=production VITE_BASE="./" VITE_ENABLE_I18N=1
          npx vite build --config vite.config.ts
        重建后实测：
          index.html   8,226 B → 5,650 B，23 处命中 → 0 处
          <title>      实况起点 PlayToStar｜… → PlayToStar
          bundle 命中  9 处 → 2 处（仅剩 COS 桶域名 efootballpsbete-…，不可去除）

  永久防呆（已写进 打包iOS工程.py 的 verify_zip）：
        ① www/index.html 的 <title> 必须**恰好等于** "PlayToStar"，
           否则直接打包失败并提示「这是网页形态产物，请用 VITE_BASE=./ 重建」
        ② www/index.html 全文不得出现 efootball / 实况足球 / konami / 实况起点 / 起点随身
        ③ bundle 内 efootball 出现次数必须**恰好等于** COS 桶域名出现次数
           （多出来的必然是 /efootball/ 路径明文，说明没走 App 形态）
        ④ bundle 内不得出现「实况足球 / konami / 实况起点 / 起点随身」

  教训（与「NODE_ENV 在 Windows 下失效」同一类）：
        构建脚本 exit 0 ≠ 产物正确。凡是靠**环境变量**切换产物形态的项目，
        必须在打包侧按**产物特征**做断言，不能相信「命令跑完没报错」。

=== 二、安全模式首帧竞态修复（P0，会直接毁掉整轮整改）===
useSafeMode() 内部是 useState(cached ?? false)：冷启动时缓存为 null，
第一帧就按 safeMode=false 渲染。对于「只挡一张肖像图」的旧场景无所谓；
但本轮要整块藏掉热讯/V观点/百科图，这一帧就是**真实泄漏**，
审核员截屏完全可能抓到。
新增 useSafeModeState() → { safeMode, resolved }：
  resolved=false 表示「还没确定」，此期间所有门控一律按隐藏处理。
写成 hideXxx = !safeResolved || safeMode 即天然 fail-safe。

【远程开关 fail-open 修复（v10 起，本版继续有效）】
原实现 fetchRemoteSafeMode() 是 fail-open——任何异常（网络错、非 2xx、JSON 解析
失败）都 return false，并且这个 false 会写进 localStorage 缓存 10 分钟。
已改为三态返回：
  true  服务器明确说开
  false 服务器明确说关
  null  没问到（网络错/超时/非 2xx/字段缺失/解析失败）
处理规则：
  · 只有明确的 true/false 才写缓存（"不确定"绝不固化成 10 分钟的"明确关"）
  · 没问到时：有历史已知值就沿用（哪怕过期），完全没有任何已知值才按安全侧
    true 兜底
  · 加 8s AbortController 超时，避免请求卡住导致页面无限等
  · 单飞 inflight Promise，避免并发重复请求

=== 四、App 内「自我声明审核关系」文案清零（本轮补漏，比官网更致命）===
官网已删「App Store 审核」字样后，回头扫 App 自身 bundle，发现还有 3 处
把「我正在被 Apple 审核」直接写在审核员能看到的界面上：

  1. Layout.tsx:90 / :96（网页端顶栏 Apple 图标 + 胶囊按钮）
       title="iOS 版正在 App Store 审核中"
       → title="iOS 版即将上线"
  2. i18n locales.ts:13 / :533
       'common.iosReview': 'iOS 审核中' / 'iOS In Review'
       → 'iOS 即将上线' / 'iOS Coming Soon'
  3. BetaAnnouncementDialog.tsx:99-108（公测公告弹窗）
       「iOS 版 App 正在苹果审核中，在此之前可直接使用网页版登录；
         受审核规则限制，网页端暂时仅支持…」
       → 「在此之前也可直接使用网页版登录；为保障账号安全，网页端目前采用…」
       EN 同步：删「The iOS app is under App Store review」「Due to review rules」

为什么这条特别危险：
  · BetaAnnouncementDialog 是**首次启动必弹**（localStorage 无
    pts_announce_v1 就 setAnnounceOpen(true)），审核员新装 App 一定看到；
  · 「我正在被 Apple 审核」等于把「这个 App 就是 4.1(a) 投诉对象」
    写在屏幕上；而 4.1(a) 判的正是「是否让审核员认为本 App 与被投诉方有关」；
  · 这是**自我指认**，比任何第三方商标都更直接。
注：Layout.tsx 那两处仅网页端渲染（isNativeApp() 时 return null），
    但 App bundle 与网页 bundle 是同一份源码产物，字符串照样进包，
    Apple 静态扫字符串一样能扫到，故必须一并清。

    outDir = path.resolve(rootDir,'dist/client') = app/dist/client，一次到位。
